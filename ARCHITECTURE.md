## 1. What this system does

A seller signs up → uploads their sales CSV/Excel/JSON → the backend cleans, validates and
stores it → the seller fine-tunes a personal XGBoost model on their own data → they get demand
forecasts with confidence bands, accuracy tracking, inventory alerts and pricing suggestions.

Four "AI modules" (the FYP framing):
1. **Data Integration** (`/upload`) — parsing, cleaning, anomaly detection, versioning, rollback.
2. **Demand Forecasting** (`/forecasting`) — XGBoost, recursive multi-day forecast, fine-tuning.
3. **Inventory Intelligence** (`/inventory`) — reorder risk alerts. *Partly mock — see §9.*
4. **Dynamic Pricing** (`/pricing`) — price recommendations. *Fully mock — see §9.*

## 2. Service topology

```
Browser
  │
  ├─ Next.js 16 App Router  (frontend/, :3000)
  │    middleware.js ─ cookie gate on /dashboard /upload /forecasting /inventory /pricing
  │    services/api.js ─ single axios instance, injects Bearer token, retries 5xx twice
  │
  ▼ http://localhost:5000/api
Express 5  (backend/, :5000)
  │    server.js mounts: /api/auth, /api (data), /api/forecast, /api/finetune, /api/store
  │    middleware/auth.js verifies JWT → req.user = {id, email, role}
  │    config/db.js ─ one shared pg Pool, used by every route
  │
  ├──────────► PostgreSQL   (11 tables, created by config/initDb.js)
  │
  ▼ http://localhost:8000    (axios, via callMLServer() in routes/forecast.js)
FastAPI  (ml/, :8000)
       main.py ─ /predict/xgboost, /predict/ensemble, /finetune, /finetune/status/{id}
       reads Postgres DIRECTLY with psycopg2 (it does not call back into Express)
       loads models from ml/models/*.pkl via joblib
```

The frontend never calls the ML server directly — Express is always the middleman.
**Two DB clients exist**: Express (`pg`) and FastAPI (`psycopg2`), both on the same tables.
The ML server loads its credentials from `backend/.env` via a `..` relative `load_dotenv` path.

## 3. The flow that matters most — forecast

`frontend/src/app/forecasting/page.jsx:300`
→ `GET /api/forecast/:productId?period=N`
→ `backend/routes/forecast.js:118` — looks up `products.category`, defaults to `United_Kingdom`
→ `POST :8000/predict/xgboost {product_id, seller_id, horizon_days, category}`
→ `ml/main.py:249`
  1. `_get_product_sales_history()` — under 30 days ⇒ **422 `insufficient_history`**
  2. `model_loader.get_model_for_seller()` — 3-tier: finetuned → category → UK fallback
  3. `forecaster.forecast_future()` — predict 1 day, append it to history, repeat
  4. accuracy: stored metric if finetuned, else backtest MAPE; `None` when unusable
  5. top-10 `feature_importances_`
→ back in Express: confidence bands = `demand ± 1.96 × residual_std`
  (fallback `×1.196 / ×0.804` if `residual_std` is missing), rows INSERTed into `forecasts`
→ JSON `{forecast:{points[],summary}, model_used, accuracy, residual_std, feature_importance}`

**Fine-tune flow:** page → `POST /api/finetune` → `POST :8000/finetune` → inserts a `finetune_jobs`
row with status `running`, returns immediately, then runs `_run_finetune_background()` as a
FastAPI BackgroundTask (warm start: `xgb.XGBRegressor(xgb_model=base_path)`, 500 trees, lr 0.01)
→ saves `xgb_finetuned_{seller_id}.pkl` + `features_finetuned_{seller_id}.pkl` → writes
`model_metrics`. The page polls `GET /api/finetune/status`. Jobs stuck over 30 min are auto-failed.

**Upload flow:** `upload/page.jsx` → `POST /api/data/upload` (multipart, field name `file`, ≤50 MB)
→ `parseFile` (csv-parser / XLSX / JSON) → `cleanData` (normalize keys → dedupe → median-fill →
IQR outlier removal → quality score = clean/total) → insert `data_uploads` row → `storeDataV2`
(per-row `validateRow`; bad rows go to `anomalies_detected`; sales deduped by the
`unique_sale_transaction` constraint) → insert `upload_versions` row → `updateFreshness`.

**The Nexus (React Three Fiber + three, no Drei).** `NexusStage` is the only import pages use: it
paints the SVG `NexusFallback` immediately, checks WebGL, and when the stage is near the viewport
and the browser is idle loads `NexusCanvas` via `next/dynamic` (`ssr:false`) — the only chunk that
contains three.js. `NexusCanvas` owns the `<Canvas>` (DPR cap, pauses with `frameloop="never"`
off-screen, `demand` under reduced motion, error boundary + context-loss → fallback, DOM hover
labels). `NexusScene` runs the camera rig (scroll stations, pointer parallax, entrance dolly,
adaptive DPR). `NexusModel.js` builds every mesh imperatively and disposes all geometry, materials
and textures; particles are one `InstancedMesh`. `nexusConfig.js` holds node definitions, layouts,
camera stations and emphasis curves. Variants: `hero` (landing, scroll-driven), `auth`
(self-orbiting), `compact` (dashboard "Nexus state", node `states` derived from API data).

Pages: `page.jsx` (public landing: pinned Nexus + 5 scroll chapters, ledger, moves, closing) ·
`login`, `signup` (public, `AuthLayout`) · `dashboard`, `upload`, `forecasting`, `inventory`,
`pricing` (protected) · `error.jsx`, `not-found.jsx`.

In-page components worth knowing: `forecasting/page.jsx` → `FineTuneCard` (5 states).
`upload/page.jsx` → `FreshnessBadge`, `Pipeline`, `ResultCard`, `RollbackModal`.
Inventory/pricing show a "Sample data" badge whenever they fall back to `MOCK_PRODUCTS`.

## 7. Database schema

- `users` — id, name, email (unique), password, role (default `seller`)
- `products` — user_id→users, upload_id→data_uploads, name, category, current_price
- `sales` — product_id, quantity, sale_date, revenue, upload_id; UNIQUE(product_id, sale_date, quantity, revenue)
- `inventory` — product_id, stock_level, reorder_threshold (default 10)
- `forecasts` — product_id, seller_id, predicted_demand, forecast_date, model_used, confidence_upper/lower
- `model_metrics` — seller_id, model_name, mae, rmse, r2_score, mape, accuracy; UNIQUE(seller_id, model_name)
- `data_uploads` — uploaded_by, file_format, total_records, clean_records, quality_score
- `finetune_jobs` — user_id, status (`pending|running|completed|failed`), metrics TEXT, error_message
- `anomalies_detected` — upload_id, seller_id, product_name, field, anomaly_type, original_value, row_number, severity (`critical|warning`), resolved
- `upload_versions` — seller_id, upload_id, version_number, rows_added/skipped/rejected, is_rolled_back
- `data_freshness` — seller_id (unique), last_upload_at, last_sale_date, total_records, freshness_score

Schema changes belong in `config/initDb.js` as `ADD COLUMN IF NOT EXISTS` — it must stay idempotent.

## 9. Known gaps and traps — read before "fixing" anything

- **`/api/pricing/recommendations` does not exist.** `pricing/page.jsx:57` calls it, the request
  fails, and the page silently falls back to `MOCK_PRODUCTS`. Module 4 is UI-only so far.
- **Inventory falls back to mock data too.** `inventory/page.jsx:44` uses `MOCK_PRODUCTS` whenever
  `/api/inventory/alerts` returns an empty array. That route is real, but only returns rows where
  `stock_level <= reorder_threshold` AND `products.user_id = req.user.id`.
- **Seller isolation is incomplete.** `/api/products`, `/api/sales` and `/api/dashboard/stats`
  return data across *all* sellers (no `user_id` filter). `/api/dashboard/stats` has no auth
  middleware at all — it only opportunistically decodes the JWT for the anomaly count. This is a
  real bug worth fixing; do not copy the pattern into new routes.
- **`/api/data/quality` has no auth middleware** either.
- **Duplicate fine-tune endpoints:** `/api/finetune` (forecast.js) and `/api/store/finetune`
  (store.js) both proxy the same ML endpoint. The frontend uses the former.
- **`/predict/ensemble` is just an alias** for `/predict/xgboost` — intentional, XGBoost-only project.
- Forecast rows are inserted on **every** forecast request, so `forecasts` accumulates duplicate
  rows for the same `(product_id, forecast_date)`; `/:productId/accuracy` groups over them.
- Adding a protected page means three edits: wrap it in `ProtectedRoute`, add the path to the
  matcher in `middleware.js`, and add a `NAV` entry in `Sidebar.jsx`.
- Base models were trained on a UK-retail dataset, so `category` is really a **country** name.
- `data/Pakistan Largest Ecommerce Dataset.csv` is 37 MB — never read it whole; sample it.
